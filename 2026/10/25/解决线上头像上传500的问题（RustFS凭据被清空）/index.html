解决线上头像上传 500 的问题（被清空的 RustFS 凭据）
2026-10-26 17:12:11 #疑难杂症 #运维 #NestJS #Docker

线上头像上传固定失败，返回 500 Internal server error；本地同一份代码却怎么传都成功。

中间还改过一版 nginx 配置，部署流水线是绿的，问题依旧。

事后发现，一次 500 背后叠着两个独立的故障：RustFS 凭据被部署流水线清空，以及 nginx 改动从未上线。

把排查过程整理下来，算是给下次遇到”本地好好的、线上不对”留条能照着走的路径。

正文

现象

三个容易误判的前提：

  1. 本地同一份代码一切正常；
  2. 上一轮改过 nginx（client_max_body_size 12m），且部署流水线是绿的；
  3. 错误体是标准 JSON，看起来像后端接口写错了。

实际上代码一行都没错，坏的是部署环节。

分清 500 是谁返回的

这是 NestJS 未捕获异常的默认响应。

如果请求没到后端，nginx 返回的是 HTML。对照表：

响应体 出处 该看哪里
{"statusCode":500,…} NestJS 未捕获异常 后端容器日志里的 stack
<html>…413 Request Entity Too Large…</html> nginx 前端容器 nginx 配置、镜像是否最新
502 Bad Gateway nginx 上游容器是否存活

于是不用再看 nginx，直接去后端要 stack：

链路很清楚：上传接口 → RustFS → bucketExists 403。

对象存储认为凭据无效，代码把异常原样抛出，Nest 兜底成 500——症状和病因之间隔了一层默认异常处理，这是第一层”假装正常”。

第一层：被清空的 RustFS 凭据

比对配置：只看长度和哈希

要确认到底是”凭据错了”还是”根本没读到凭据”，三处都要看：

  • 服务器上的 /opt/deploy/nest-admin/.env（部署生成）
  • 1Panel 里 RustFS 应用自己的 .env（真实凭据）
  • 后端容器环境变量（最终生效值）

不打明文，用”长度 + sha256 前 12 位”比对就够定位：

来源 RUSTFS_ACCESS_KEY RUSTFS_SECRET_KEY
服务器 .env 空（长度 0） ← 问题 正常
1Panel RustFS 应用 正常 正常
后端容器环境变量 空 正常

Secret 在、Access Key 是空串，MinIO 客户端用空 AK 签名，服务端当然回 Valid and authorized credentials required。

顺带用 curl 裸访问一次 S3 端口，未认证返回 403，说明服务本身活着，可以排除”RustFS 挂了”这个方向。

空值哪来的：流水线每次都覆盖 .env

.env 不是手工维护的，而是 deploy.yml 在服务器上现生成的：

GitHub Actions 对不存在或为空的 Secret 不报错，直接渲染成空字符串。于是每次部署都会把原本可用的 .env 覆盖成坏版本。

这解释了本地与线上的矛盾：本地配置完整，线上坏的是”部署”这个动作本身——Secret 缺失，而流水线对此零校验、零提示。

定位：容器里跑的还是旧配置

验证

头像 URL 形如 /profile/nest-admin/avatar/xxx.png，由 nginx 反代到 RustFS。”上传成功”和”能显示”是两件事，两个都要验。

附：没有登录态时怎么测鉴权接口

排查时手上没有账号密码。鉴权逻辑是”JWT 验签 + 用 payload 里的 uuid 查 Redis”，所以从 Redis 拿一个会话 uuid，用容器里的 JWT_SECRETKEY 自己签一个合法 token：

两点注意：这是越权手段，只用于自有服务器，用完不留 token；上传接口会真的写库——我的 admin 头像就被测试图覆盖了，最后查 sys_upload 找回真实记录还原。测试数据一定要清，否则下次排查先要面对自己上次制造的噪音。

结语

下次再遇到”本地好好的、线上不对”，按顺序问四个问题就够了：

  1. 这个错误是谁返回的——500 JSON 进了后端，413 HTML 被 nginx 拦在门口，502 上游不可达；
  2. 容器里的实际配置是什么——宿主机文件对不算数；
  3. 运行时是不是最新——看容器创建时间，别信镜像 tag 和流水线状态；
  4. 直连和经代理分别什么结果——分清后端问题和代理问题。

这次最难的地方不在技术，在信号被静音：

  • 403 被包装成 500，指向了错误的层；
  • 构建失败被兜底吞掉，指向了错误的状态。

把静音的信号重新打开——读容器里的实际配置、读日志里的原始异常、按链路分开测——问题就藏不住了。
